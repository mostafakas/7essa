# المعمارية

```
المتصفح (Next.js RTL)
   │  نفس النطاق: الكوكيز httpOnly بلا CORS
   ▼
Vercel ─ hessa-web: middleware يمرر /api/* ومعه عنوان العميل + سر مشترك
   │
   ▼
Vercel ─ hessa-api: NestJS كدالة واحدة (fra1) ─── Vercel Cron (يوميًا)
   │  دور hessa_app المقيد + set_config(app.user_id / app.workspace_id) لكل معاملة
   ▼
Neon Postgres عبر pooler (RLS + دوال SECURITY DEFINER + مشغلات حماية)
```

- **بلا حالة في الخادم**: لا طوابير ولا ذاكرة مشتركة؛ كل شيء في Postgres، فتعمل أي نسخة من الدالة بنفس النتيجة.
- **الإشعارات** تُكتب مباشرة في جدول `notifications` بدفعات (`createMany`) داخل الطلب نفسه، ويقرؤها التطبيق.
- **إعدادات المنصة** صف واحد في `platform_settings` مع كاش 60 ثانية لكل نسخة.
- **المهمة اليومية** (`/api/v1/cron/daily`) محمية بـ`CRON_SECRET` وتعمل مرة واحدة يوميًا حتى لو أُعيدت.

## المفاهيم الأساسية

- **مساحة العمل**: سنتر (`CENTER`) أو مدرس خاص (`TEACHER`). كل البيانات التشغيلية تحمل `workspaceId`.
- **العضوية**: مستخدم واحد قد يكون مالكًا لسنتر ومدرسًا في آخر وولي أمر في نفس الوقت. الدور يُحدد لكل مساحة.
- **الهوية الموحدة للطالب**: الطالب كيان عام مربوط برقم ولي الأمر. التسجيل في مكان جديد بنفس (ولي الأمر + الاسم + الصف) يربط نفس الهوية بدل تكرارها، فيتابع ولي الأمر كل شيء من حساب واحد.
- **الاشتراك (Enrollment)**: ربط الطالب بمجموعة داخل مساحة عمل، بكود من 6 أرقام وخصم وحالة وموافقة ولي الأمر.

## الأدوار والصلاحيات

الصلاحيات تُفرض في الخادم (`common/permissions.ts`)، والواجهة تخفي ما لا يخص الدور فقط لتحسين التجربة.

| الدور | يرى ويفعل |
|---|---|
| المالك | كل شيء |
| المدير | كل شيء عدا إعدادات المساحة |
| المدرس | طلاب مجموعاته، الحضور، الامتحانات، كشف حسابه |
| الاستقبال | التسجيل، الحضور، التحصيل، الخصم في حدود، طلب الإلغاء، الوردية، المتأخرات |
| المحاسب | التحصيل، المصروفات، التقارير، المتأخرات، التسويات والصرف |
| مساعد المدرس | طلاب مدرسه، الحضور، تصحيح الامتحانات |
| المتابعة | الطلاب والمتأخرات للتواصل مع الأسر |

## الحسابات والدخول

- **حساب واحد لكل شخص** (`users`): يدخل باسم مستخدم أو برقم موبايله، وقد يكون مالكًا لسنتر ومدرسًا في آخر وولي أمر معًا.
- **كلمات المرور**: `scrypt` (N=16384, r=8, p=1) بملح عشوائي، بصيغة ذاتية الوصف تسمح برفع المعاملات لاحقًا.
- **كلمات مؤقتة**: كل حساب يُنشأ من السنتر أو الإدارة يحصل على كلمة مثل `kmtr-4827` تظهر مرة واحدة للطباعة أو النسخ، و`mustChangePassword` يمنع أي استخدام قبل تغييرها.
- **من يصدر بيانات الدخول**: السنتر لأعضاء فريقه ولأولياء أمور وطلاب مساحته **قبل أول دخول فقط**؛ بعده، إعادة التعيين من إدارة المنصة وحدها.
- **الجلسات**: JWT لمدة 15 دقيقة + رمز تجديد 30 يومًا يُدوَّر مع كل استخدام.

## فريق إدارة المنصة

| الدور | الصلاحيات |
|---|---|
| مالك المنصة `SUPER_ADMIN` | كل شيء، وإدارة فريق المنصة والإعدادات وحذف المدفوعات |
| الدعم `SUPPORT` | المساحات والفرق والمستخدمون وكلمات المرور والإعلانات |
| المالية `FINANCE` | الخطط والأسعار والمدفوعات وحدود الاشتراك |
| مشاهد `VIEWER` | قراءة فقط |

الصلاحيات تُفرض في الخادم (`platform/platform-permissions.ts` و`PlatformGuard`)، ولا يستطيع أحد غير مالك المنصة تعديل حساب عضو في فريق المنصة، ولا يمكن إيقاف أو تخفيض آخر مالك نشط.

## الاشتراك وحالة الوصول

`common/access.ts` يحسب لكل مساحة حالة لحظية من (`status`, `trialEndsAt`, `paidUntil`, `graceDays`):

| النتيجة | الحالات |
|---|---|
| `FULL` | تجربة سارية، اشتراك ساري أو مفتوح، فترة سماح |
| `READ_ONLY` | انتهت التجربة، انتهى الاشتراك بعد السماح، متوقف مؤقتًا |
| `BLOCKED` | موقوف |

`WorkspaceGuard` يرفض أي طلب كتابة (غير GET) في `READ_ONLY` برمز `READ_ONLY`، وأي طلب في `BLOCKED`. حدود الخطة (الطلاب النشطون وأعضاء الفريق) تُفحص في `LimitsService` عند التسجيل والإضافة، ويمكن تخصيصها لكل مساحة.

## تدفقات رئيسية

**الحضور عند الباب**: قارئ USB أو كاميرا أو كود ← `POST /attendance/scan` ← التحقق من توقيع الرمز وإصداره ← فتح الكشف تلقائيًا ← تسجيل حاضر/متأخر ← ختم على الشاشة بحالة الاشتراك ← إشعار وصول لولي الأمر داخل التطبيق. دون اتصال تُحفظ العمليات بمعرف فريد وتُرسل عبر `/attendance/sync` دون تكرار، وتصحح الغياب التلقائي إن أُغلق الكشف قبل المزامنة.

**التحصيل**: وردية مفتوحة ← بحث بالكود ← حساب المتبقي بعد الخصم ← قفل (الاشتراك + الشهر) ← رقم تسلسلي ← إيصال حراري 80 مم ← إشعار لولي الأمر.

**التسوية الشهرية**: العقد الساري ← إيصالات الشهر السارية (المعلق إلغاؤها يُستبعد ويُنبه عنه) ← ساعات القاعات ← السلف (مع ترحيل الزائد) ← `calculateSettlement` ← كشف مسودة ← تأكيد أو اعتراض المدرس ← اعتماد الإدارة ← صرف (النقدي يُسجل مصروفًا على الوردية).

**الامتحان الإلكتروني**: نشر ← الطالب يبدأ ← ترتيب أسئلة واختيارات خاص بكل طالب (بذرة ثابتة) ← ورقة بلا إجابات ← حفظ محلي أثناء الحل ← تسليم ذري ← المفتاح يُفتح بعد التسليم فقط ← تصحيح ← الدرجة حسب إعداد المدرس، والإجابات النموذجية بعد الإغلاق ← تحليل السهولة والتمييز للمدرس.

## قرارات تصميم

- **Prisma + SQL يدوي للأمان**: النموذج في Prisma، والسياسات والدوال والمشغلات والصلاحيات في ترحيلات SQL لأن Prisma لا يديرها.
- **الدور المقيد يُشتق تلقائيًا**: الخادم يأخذ `DATABASE_URL` ويبدل اسم المستخدم بـ`hessa_app` وكلمة مروره (`config/database-url.ts`)، والترحيلات وحدها تستخدم حساب المالك. صفحة «صحة النظام» تتحقق من ذلك لحظيًا.
- **الوحدات البحتة منفصلة عن الإطار** (المال، التسويات، الجدولة، التصحيح، الـQR، كلمات المرور، حالة الوصول) لتُختبر بدون قاعدة بيانات.
- **الواجهة على نفس النطاق**: middleware في Next.js يمرر `/api` للخادم، فتبقى الكوكيز httpOnly وSameSite دون CORS، ويصل عنوان العميل الحقيقي بسر مشترك.
- **دالة واحدة للخادم**: تطبيق Nest يُهيأ مرة لكل نسخة دافئة (`serverless.ts`) ويُعاد استخدامه، مع اتصالات قليلة عبر pooler (`connection_limit=5`).
- **التوقيت**: كل الأوقات تُخزن UTC وتُعرض وتُحسب أيامها بتوقيت `Africa/Cairo`.
