# النشر على GitHub و Vercel

المنصة كلها تعمل على **GitHub** (الكود والفحص التلقائي) و**Vercel** (الواجهة والخادم والمهمة اليومية وقاعدة البيانات عبر Storage). لا يوجد Docker ولا Redis ولا خوادم تديرها بنفسك.

```
GitHub (main)
   │ دفع ← نشر تلقائي
   ▼
Vercel ─ مشروع hessa-web   (apps/web)  Next.js + middleware يمرر /api/*
   │                                     مع عنوان العميل وسر مشترك
   ▼
Vercel ─ مشروع hessa-api   (apps/api)  NestJS كدالة واحدة + Cron يومي
   │                                     دور hessa_app المقيد (RLS)
   ▼
Vercel Storage ─ Neon Postgres (فرانكفورت)
```

> قاعدة البيانات تُنشأ من داخل Vercel (تبويب **Storage** ← Neon). الفوترة والإدارة من حساب Vercel نفسه، وNeon هو محرك Postgres الذي يوفره Vercel حاليًا.

> **خطة Vercel**: الخطة المجانية (Hobby) للتجربة والاستخدام غير التجاري فقط حسب شروط Vercel. عند تشغيل المنصة تجاريًا مع سناتر حقيقية تحتاج خطة **Pro**.

---

## 1) GitHub

1. أنشئ مستودعًا خاصًا (Private) وارفع المشروع:
   ```bash
   git init && git add . && git commit -m "حصّة"
   git branch -M main
   git remote add origin git@github.com:ORG/hessa.git
   git push -u origin main
   ```
2. شغّل مرة واحدة على جهازك `npm install` ثم ارفع `package-lock.json` المحدث (حُذفت حزم Redis/BullMQ وpg).
3. ملف `.github/workflows/ci.yml` يعمل تلقائيًا مع كل دفعة وطلب دمج: فحص الأنواع، الاختبارات، البناء، وتطبيق كل الترحيلات على قاعدة نظيفة.
4. يُفضل تفعيل **Branch protection** على `main` بحيث لا يُدمج شيء قبل نجاح CI.

## 2) مشروع الخادم `hessa-api`

1. في Vercel: **Add New ← Project** واختر المستودع.
2. **Root Directory**: `apps/api` — Framework Preset: **Other** (باقي الإعدادات تأتي من `apps/api/vercel.json`).
3. قبل أول نشر افتح تبويب **Storage ← Create Database ← Neon (Postgres)**:
   - المنطقة: **Frankfurt (eu-central-1)** لتكون بجوار دالة الخادم (`fra1`).
   - اربطها بالمشروع لكل البيئات أو **Production فقط** (انظر «المعاينات» بالأسفل).
   - يضيف Vercel تلقائيًا `DATABASE_URL` (عبر pooler) و`DATABASE_URL_UNPOOLED` (مباشر).
4. **Settings ← Environment Variables** (بيئة Production). لتوليد أسرار قوية: `npm run setup:env -- --print`

   | المتغير | القيمة |
   |---|---|
   | `NODE_ENV` | `production` |
   | `APP_DB_PASSWORD` | سر عشوائي 24+ حرفًا (كلمة مرور الدور المقيد) |
   | `JWT_ACCESS_SECRET` | سر عشوائي 48 حرفًا |
   | `QR_SECRET` | سر عشوائي 48 حرفًا (تغييره يُبطل كل الكارنيهات المطبوعة) |
   | `CRON_SECRET` | سر عشوائي (Vercel يرسله للمهمة اليومية تلقائيًا) |
   | `PROXY_SHARED_SECRET` | سر عشوائي، **نفس القيمة** في مشروع الواجهة |
   | `REQUIRE_PROXY` | `true` |
   | `WEB_ORIGIN` | رابط الواجهة، مثل `https://hessa.vercel.app` (أو نطاقك، ويقبل أكثر من رابط بفاصلة) |
   | `COOKIE_SECURE` | `true` |
   | `TRUST_PROXY_HOPS` | `1` |
   | `BOOTSTRAP_ADMIN_USERNAME` | اسم دخولك كمالك للمنصة، مثل `admin` |
   | `BOOTSTRAP_ADMIN_PASSWORD` | كلمة مرور قوية (8+ حروف وأرقام) |
   | `BOOTSTRAP_ADMIN_NAME` | اختياري: اسمك الظاهر |

5. **Deploy**. أمر البناء (`scripts/vercel-build.mjs`) ينفذ بالترتيب:
   `prisma generate` ← `nest build` ← `prisma migrate deploy` ← إنشاء/ضبط الدور `hessa_app` ← إنشاء حساب مالك المنصة (مرة واحدة فقط).
6. للتأكد: افتح `https://<hessa-api>.vercel.app/api/v1/health` ← يجب أن يرد `ok`.

## 3) مشروع الواجهة `hessa-web`

1. **Add New ← Project** بنفس المستودع مرة ثانية.
2. **Root Directory**: `apps/web` — Framework: **Next.js**.
3. المتغيرات:

   | المتغير | القيمة |
   |---|---|
   | `API_INTERNAL_URL` | رابط مشروع الخادم، مثل `https://hessa-api.vercel.app` |
   | `PROXY_SHARED_SECRET` | نفس قيمة مشروع الخادم |

4. **Deploy**، ثم ارجع لمشروع الخادم وتأكد أن `WEB_ORIGIN` يطابق رابط الواجهة الفعلي (وأعد نشره إن غيرته).

## 4) أول دخول

1. افتح رابط الواجهة ← ادخل بـ`BOOTSTRAP_ADMIN_USERNAME` وكلمة المرور.
2. **إدارة المنصة ← الإعدادات وصحة النظام**: كل الفحوص يجب أن تكون «سليم»، وأهمها **عزل بيانات السناتر (RLS)**.
3. اضبط رقم الدعم وأيام التجربة وأيام السماح، ثم **الخطط والأسعار**.
4. أنشئ أول سنتر من **السناتر والمدرسون ← مساحة عمل جديدة**؛ تظهر لك بيانات دخول المالك (اسم مستخدم + كلمة مرور مؤقتة) لتسلمها له.
5. يُفضل حذف `BOOTSTRAP_ADMIN_PASSWORD` من Vercel بعد أول دخول (لم يعد مطلوبًا) وإنشاء حسابات منفصلة لفريقك بأدوار الدعم والمالية.

## 5) النطاق الخاص (اختياري)

- اربط نطاقك (مثل `app.hessa.eg`) بمشروع **الواجهة** فقط من **Settings ← Domains**.
- حدّث `WEB_ORIGIN` في مشروع الخادم للنطاق الجديد (يمكن إبقاء رابط vercel.app معه بفاصلة) وأعد نشر الخادم.
- لا حاجة لنطاق لمشروع الخادم: المستخدمون لا يصلون إليه مباشرة (`REQUIRE_PROXY=true`).

## 6) المهمة اليومية (Cron)

معرفة في `apps/api/vercel.json`: كل يوم 01:00 UTC (03:00 أو 04:00 بتوقيت القاهرة) تستدعي `/api/v1/cron/daily`:
- تنبيه ملاك ومديري المساحات قبل انتهاء التجربة أو الاشتراك بـ 7 و 3 و 1 يوم.
- تنظيف جلسات الدخول المنتهية.

نتيجة آخر تشغيل تظهر في صفحة **صحة النظام**. انتهاء الاشتراك نفسه لا يحتاج المهمة: الحالة تُحسب لحظيًا مع كل طلب.

## 7) المعاينات (Preview Deployments)

كل فرع أو طلب دمج يحصل على رابط معاينة تلقائيًا. **أمر البناء لا يطبق الترحيلات إلا في Production**، لكن كود المعاينة سيعمل على نفس القاعدة لو كانت متغيراتها متاحة لبيئة Preview. اختر أحد الحلين:

- **الأبسط**: اجعل متغيرات قاعدة البيانات لبيئة **Production فقط**؛ المعاينات للواجهة تكفي غالبًا.
- **الأفضل للفريق**: فعّل في تكامل Neon خيار إنشاء **فرع قاعدة بيانات لكل معاينة**، وأضف `MIGRATE_ON_BUILD=true` لبيئة Preview فقط، مع نسخ باقي المتغيرات لها.

## 8) النسخ الاحتياطي والاسترجاع

- Neon يحتفظ بسجل تغييرات يسمح بالاسترجاع لأي لحظة خلال مدة الاحتفاظ بخطتك (من لوحة Neon ← **Restore**)، والأفضل الاسترجاع لفرع جديد ومقارنته قبل الاعتماد.
- جرّب الاسترجاع مرة كل شهر على فرع منفصل.
- حدث مهم: لا تشغّل `db:seed` على قاعدة الإنتاج (يرفض العمل مع `NODE_ENV=production`).

## 9) ترحيلات جديدة (تعديل قاعدة البيانات)

```bash
# 1) عدّل apps/api/prisma/schema.prisma
# 2) أنشئ ملف الترحيل على قاعدة التطوير وراجعه
npm run db:new-migration -- --name وصف_التعديل
# 3) أضف له يدويًا ما يلزم: GRANT لدور hessa_app وسياسات RLS للجداول الجديدة
# 4) ارفع على فرع ← CI يطبقه على قاعدة نظيفة ← دمج في main ← يُطبق على الإنتاج مع النشر
```

## 10) استرجاع حساب مالك المنصة

لو فُقدت كلمة المرور ولا يوجد مالك آخر:
1. في مشروع الخادم أضف `BOOTSTRAP_ADMIN_RESET=true` مع `BOOTSTRAP_ADMIN_USERNAME` و`BOOTSTRAP_ADMIN_PASSWORD` جديدة.
2. **Redeploy** لآخر نشر في Production.
3. ادخل، ثم **احذف** `BOOTSTRAP_ADMIN_RESET` فورًا وأعد النشر.

## حل المشكلات

| العرض | السبب والحل |
|---|---|
| «إعدادات البيئة غير صحيحة» في سجل الدالة | متغير ناقص أو قصير؛ الرسالة تذكر اسمه |
| «APP_DB_PASSWORD مطلوب في الإنتاج» | أضفه في مشروع الخادم وأعد النشر (البناء ينشئ الدور) |
| فحص RLS «يحتاج ضبط» | التطبيق يعمل بحساب المالك: تأكد من `APP_DB_PASSWORD` ومن نجاح خطوة setup-db في سجل البناء |
| «الوصول المباشر للخادم غير مسموح» | `PROXY_SHARED_SECRET` مختلف بين المشروعين، أو `API_INTERNAL_URL` خطأ |
| 403 عند الدخول (Origin) | `WEB_ORIGIN` لا يطابق رابط الواجهة حرفيًا (بدون / في النهاية) |
| البطء في أول طلب بعد فترة | بدء بارد للدالة وقاعدة Neon بعد الخمول؛ طبيعي ويتحسن مع الاستخدام |
